# 双表对比·补充技巧（2026-08-24 三轮迭代后）

本文件是 dual-semester-compare / dual-semester-name-matching 两个 reference 的**增量补充**，
记录用户确认后重跑、加日均列、以及"文件有修改吗"的验证方法。

## 1. 用户三条确认后的重跑流程

对比表初版交付后，用户通常会给一批"待确认项"的答复。本次三项答复及其落实方式：

| 用户答复 | 落实方式 |
|---|---|
| "9人金额确实为0" | 照表保留，不改金额，汇总说明里注明"用户确认确实为0" |
| "这两位是同一人，名字手误打错" | MERGE dict 别名映射合并（见下） |
| "25秋的那8人正常" | 硬编码行照表保留，汇总说明注明"用户确认正常" |

## 2. 同一人手误合并（MERGE dict 实现）

疑同名**先标注不合并**，等用户确认"是同一人"后，用别名映射而非改表：

```python
MERGE = {'徐惠婷': '徐慧婷', '李佳慧': '李嘉慧'}   # 26春名 → 25秋名（用户确认手误）
target = MERGE.get(p['name'], p['name'])           # 匹配前先映射
ms = [f for f in fall if f['name'] == target]
# len(ms)==1 且 target != p['name'] → status='ok_merge'，备注「同一人手误合并」
```

- 合并后两行变一行：25秋金额取 25秋 行、26春金额取 26春 行，差额/日均照算
- 状态分布随之变化（本次：仅25秋 12→10、仅26春 20→18，新增 ok_merge=2），
  **重跑后必须重新核对总行数与状态分布**（211 = 179 唯一 + 2 按年级 + 2 合并 + 18 + 10）
- 总金额不变（合并只是显示层，不是改源数据）

## 3. 双日均列（用户会要求两学期日均都算）

交付物 Excel 的金额列旁边加日均列，**两个学期都要**：
- 25秋日均 = 25秋金额 ÷ 97 天（FALL_DAYS）
- 26春日均 = 26春金额 ÷ 84 天（SPRING_DAYS）
- 天数常量放脚本顶部 `FALL_DAYS, SPRING_DAYS = 97, 84`，不要写死在算式里
- 合计行也加日均（25秋 13292.58 / 26春 13343.25）
- 列顺序：25秋金额 → 25秋日均 → 26春金额 → 26春日均 → 差额 → 备注
- 有趣的结论点：25秋 总金额高但日均反而略低（天数多）——汇报时可点出

## 4. "文件有修改吗"的验证方法（用户会问源表是否被动过）

用户很在意源表（25秋555.xlsx 等）是否被脚本改过。三步自证：

1. **grep 所有脚本的 save 调用**：`grep -rn "save" /tmp/*.py | grep -v json`，
   看 wb.save() 的目标路径是否含源表。本次 4 处 save 全是 1稿/新输出文件，源表只 load。
2. **对比脚本首次运行时间 vs 文件 mtime**：`ls -la --time-style=full-iso 源表`。
   本次源表 mtime 15:32，脚本首跑 15:34 → 修改在脚本之前，不是脚本干的。
3. **core.xml 元数据**：`zipfile` 读 `docProps/core.xml` 的 created/modified 时间戳，
   佐证文件何时被"保存"过（可能是用户微信另存/WPS 打开保存，不是我们）。

结论模板：我的脚本全部只读（load_workbook(data_only=False) 从不写回）；但文件内部
元数据显示今天 HH:MM 有一次保存——那不是脚本干的（脚本更晚才跑），可能是有同事/
家人打开过。**要如实说明，不替用户下结论**。
