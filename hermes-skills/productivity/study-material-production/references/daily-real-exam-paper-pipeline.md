# 每日真题练习卷流水线（数学 30 题 + 英语完形/阅读）

用户每天要一份练习卷：数学 30 题（1—20 问题求解、21—30 条件充分性判断）+ 英语（完形填空 20 题 + 阅读理解 2 篇 × 5 题 = 30 题）。本文件是这类卷子的取源、组装、复核规程。

## 硬性口径（每一份卷子都适用，不得逐卷重议）

1. **难度下限=真题难度。** 对标管理类联考真题（中等偏难～难），禁基础题、禁纯公式套用。每道题标 `src`（真题改编 / 仿真），不得以基础题充数。用户对「太基础了」会直接不满——这是最容易踩的雷。
2. **选年避重。** 英语真题避开近五年（滚动窗口），且不得与前一天卷子用同一年；逐年往前推（如 …2016 → 2015 → 2014）。一套真题的多个 Text 拆到多天做：每天给完形 + Text 1、Text 2（第 21—30 题），Text 3、Text 4 留给下一套，并在卷首说明这样拆。
3. **答案字母跨版本会漂移。** 同一道真题在不同真题册里 A/B/C/D 会对调（选项内容相同、次序不同）。因此：
   - 卷首提示写明「本卷答案字母一律以本文件选项顺序为准；与别的册子对照请看选项文本，不要只看字母」；
   - 每题解析同时给「答案字母 + 选项文本」，答案速查也带文本；
   - 组装前先校验所用源是否保留原卷选项顺序——校验法：该源给出的答案字母与官方答案逐题一致，即可认为保留原序；不保留原序就得重排或换源。
4. **答案分布不得机械循环。** 声明分布并做到均衡（如 30 题里 A/B/C/D 各 7～8；PS 部分 A/B/C/D/E 各 4、DS 部分各 2）。用脚本核对，不要在脑中数。
5. **DS 选项口径跨卷不变**：A=条件(1)充分但(2)不充分；B=条件(2)充分但(1)不充分；C=单独都不充分、联合充分；D=各单独充分；E=联合亦不充分。题干里条件编号不得重复（避免出现「（1）(1)」这类残迹）。
6. **文档版本约定**：文件名末尾 + 文档头都标版本号，修订递加（v1.0→v1.1），改名不改号；入口/总览文件同步递加版本并登记新卷。
7. **解析置文末（最后一页）**，做题区绝不给答案。解析应含：答案速查、逐题解析（附定位句与干扰项分析）、全文参考译文、生词与短语、长难句拆解、错题与生词本。
8. **存放**：练习类文件进 Obsidian vault 的 `MBA/练习/`，并在 `98 hermes` 留一份；一份卷子=一个文件，题面+文末解析永不拆成「试卷版/解析版」两个文件。

## 真题源：GitHub 结构化数据集（优先通道）

搜索通道经常只回标题/摘要页，拿不到完整原文。不要在「换个引擎再试一次」上耗时间。

- 主源：GitHub 仓库 `LIziak112/structured-kaoyan-english`，raw 直取 `https://raw.githubusercontent.com/LIziak112/structured-kaoyan-english/main/data/<年>-<卷>/<年>-<卷>.md`（`-2` = 英语二）。文件含 Section I 完形（正文 20 处 `{{n}}` 占位）、Section II Part A 的 Text 1—4（含题号、选项）、`> **答案**：X` 行、`<details>` 解析、段落级译文——字段成对，可脚本解析。
- 换年份/换科目/再找一个校对源：`api.github.com/search/repositories?q=考研英语真题` 搜仓库 → `api.github.com/repos/<owner>/<repo>/git/trees/<branch>?recursive=1` 列文件树 → 单文件走 `raw.githubusercontent.com`。
- 原卷题号映射：英语二 Section II Part A 的 Text 1—4 = 真题第 21—25 / 26—30 / 31—35 / 36—40 题；本卷统一重排为第 21—30 题，解析里注明原题号。
- 答案抽取：`scripts/extract_kaoyan_answers.py`（按 Section/Text 切片 → 正则只认独立成行的答案行 → 落 JSON）。

**先取官方答案，再写卷。** 动手写卷（或把写卷派给子代理）之前，先自己用脚本把官方答案抽成 JSON；成品出来后逐题比对。两条理由：一是子代理的「复核通过」是自述、不算证据，比对物必须握在自己手里；二是答案字母会随选项次序漂移，比对以选项**文本**为准（见硬性口径 3）。

**跨年拆卷**：上一套只用了某年度的 Text 1/Text 2，本套就续用同年度 Text 3/Text 4，完形另取再往前一年的 Section I；卷首写明「本卷完形取 X 年、阅读取 Y 年 Text 3/4，该原卷还剩哪几篇」。

## 步骤

1. **选题源**：优先真题原文，不要自编题充数；先翻练习目录看已用过哪些年份，避免重复。
2. **抓源 + 交叉校对**：首选下面「真题源」节里的 GitHub 结构化数据集（raw 直取、含答案与译文、字段成对、可脚本解析）；数据集拿不到时才退到搜索 + urllib/curl 抓页。至少两源，按文本干净度挑主源，另一源做校对；浏览器通道超时不要死等。
3. **清洗 OCR 噪声**：只统一空格与标点，逐项修明显错字（`signall`→signal、`ungreatful`→ungrateful、`Sciense`→Science、`thay`→that），并在卷首注明「原文照录，仅统一空格与标点」。
4. **组装成长文档时分片写**：把卷头+答题卡+卷面、题目、解析分别写到 `/tmp/*.md`，再用 `cat p1 p2 p3 > 成品.md` 合并。单次巨量 `write_file` 会被截断或压缩，分片写能在中途保存进度。
5. **独立复核脚本必跑**，检查项：题号连续无缺、每题选项数正确（4 个）、答案字母与选项文本一致、答案分布与声明一致、DS 题干条件编号不重复、成品行数/字节数合理。0 FAIL 才算完成。**另加反抽校验（成本极低、必须做）**：从成品 md 反抽三处互证——答案速查行、解析标题字母（`**n. X`）、题面选项，与自持官方 key 逐题比对；三处一致才算过。数学卷与前两日卷做共享行查重。
6. **三处副本一致性**：`98 hermes` 工作副本 + vault `MBA/练习/` + vault `raw/sources/` 三份必须 md5 相同（子代理常只写其中一两处）。
6. **交付**：成品文件直接附给用户（`MEDIA:` 路径），并说明难度口径、选年、答案分布；不要只给摘要或骨架。

## 坑

- 单次超大 `write_file` 会被截断/压缩 → 分片 + `cat`。
- 复制来的答案字母不可直接信：选项常与题号错位（字母藏在括号里、题号换行、`[q` 等残迹），必须用答案**文本**反查题号。
- 网页源常见的 OCR 错字会污染选项（如 `resis`→resist、`predictl`→predict），不修就进卷子，用户做题会卡住。
- 浏览器抓页偶尔 IPC 超时：改用 web 搜索 + urllib/curl 抓页做主通道，校对照样能完成。
- 不要为了「看起来完整」把 Text 3/Text 4 也塞进当天卷子——那是下一套的素材，塞进去用户会觉得量爆炸。
- 别在搜索引擎上连试十几个：拿到的多是标题摘要页，还要清洗 OCR 噪声；直接走 GitHub 数据集 + raw 通道更快更干净。
- 答案不要靠「读一遍记下来」：写脚本按 Section/Text 切片抽字母并落 JSON，出卷后逐题比对，比对以选项文本为准。
- 长文组装（卷头+答题卡+题面+解析）量大，可以并行委派子代理出卷，但**答案抽取和最终比对必须自己先做/自己做**——委派的是写作，不是验收。
