# 高绩效调薪申请理由：论证写法（上级评审口径）

适用：季度高绩效调薪申请表「申请理由」的撰写与返修。岗位覆盖 DE / IE / AE / 数据开发 / 维优运维。评审人是软件工厂厂长与公司高层，口径固定，返修一次的成本很高，第一次就要按这个写。

配套：`performance-assessment-model.md` 管「考核模型怎么设计」，本文件管「已有 A 的人怎么写材料让他过」。

## 一、核心判断

材料不是工作流水账，只回答两件事：

1. 这个人**相对同岗位、同工龄的正常预期**多做出了什么；
2. 这件事对**部门整体经营**（效率／收入／稳定性／能力沉淀）产生了什么价值。

评审人一眼认出的「AI 味」= 把工作事项用 AI 重新分段，每段末尾用「体现出较强的××能力／××意识／××担当」收尾。**形容词不是绩效点。** 「跨项目快速支援」「主动承担持续交付职责」这类是身份描述，不是贡献。

评审人的原话标准是「论迹不论心」：只看客观产出和机制，辛苦、加班、态度好本身不算绩。

## 二、每个绩效点的四要素

| 要素 | 内容 | 缺了会怎样 |
|---|---|---|
| ① 基线 | 同期新人第 1 个月在做什么／原计划几人天／岗位职责是否要求做这事 | 没基线，「表现突出」就是空话 |
| ② 超额动作 | 具体行为 + 时间 + 范围 | 只剩形容词 |
| ③ 可验证结果 | 数字、评审通过、零延期、验收完成、零严重现网问题 | 会被当场追问「成果是什么」 |
| ④ 部门价值 | 效率提升／收入节点／稳定性／能力可复制 | 变成个人好人好事 |

## 三、硬规则

1. **只写超出同岗位、同工龄预期的事**，本职范围内的一律不写。写本职反而暴露管理问题。
2. **每一条必须有对照基准**。没有基线就补，补不出来就删这一条，不要用形容词撑。
3. **删尽形容词**，一律改成可观察行为 + 结果。「较强的独立支撑能力」→「他能独立判断测到哪够，别人要等 PM 拍」。
4. **禁止写「因人员离职／人员陆续调动／紧急支援」作为功绩**。评审人会反推：如果人不流动就不需要他，那只是主管排班不到位。改写成「人力按计划撤出后，保障了什么结果」。
5. **重构、攻坚必须写清解决了什么问题**：效率提升了？对人的要求／人数下降了？后续谁接手不用重新摸？只写「攻坚复杂业务功能重构，推动核心模块成功上线」会被问「不重构就上线不了吗」。
6. **删除非重点客户、非本部门主业的工作**。评审人会直接判为「非重点客户的非主业工作，只能说闲得慌」，还会稀释真正的绩效点。
7. **结尾落到部门激励导向**：这次奖励的是什么行为，全团队看得懂、学得到。调薪本质是奖励信号，不是补偿。

## 四、结构模板

员工信息 → 近六月月度绩效 → 申请理由：

- **开头一句加粗的「绩效点」**，让评审人只读这句也能得出结论（这一句是全篇最重要的投资）。
- 分条 (1)~(n)，每条只打一个绩效点。
- 最后一条不再叫「综合评价」（原稿常见病：复述罗列），改成**部门激励导向**。
- 每人 3~4 个绩效点，最多不超过 5 个。点多必散。

写法上把「岗位默认做什么 / 他额外做了什么」写在同一句里做对照，比分开叙述有效得多。

## 五、分岗位的「超出预期」长什么样

| 岗位 | 岗位默认预期 | 真正的超预期长什么样 |
|---|---|---|
| DE 新人 | 第 1 个月学基础模块、跟随老 DE 配置 | 同期还在学时他已在现场独立交付；掌握研发侧才有的能力（如 Skill 开发）且**反过来教同批新人**（越过「新人学习期」） |
| DE 骨干 | 按设计做配置、按计划上线 | 设计方案缺失时反向还原业务逻辑再重构，把「谁接手都要重摸一遍」的模块变成有依据、可迭代的模块；单位产出效率明显高于基准 |
| IE | 按测试计划执行用例、按分配模块交结果 | 做**测试分析与范围决策**（定测什么、测到哪够、哪一天不能松）；把质量左移到变更／需求评审；关键节点带队 |
| 维优／运维 | 值班、处理问题单 | 落点只有两个：**验收过得去（收入）** 和 **项目离得开人（可移交）**。形容「人好、敬业」不构成业绩 |

## 六、评审人视角自检三问

1. 这句话换成同岗位另一个人的名字还成立吗？成立 → 不是绩效点。
2. 有没有基线？没有 → 补基线或整条删掉。
3. 结果能不能被追问出数字或事实？不能 → 在交付里单列「待补数据」，并写明追问风险，不要含糊过去。

## 七、交付形态（用户偏好）

- 要 **markdown**，明确告知「不用在 Word 里改」，可直接贴回表格。
- 一次给两份：**重写正文** + **原文/改后比对表**。比对表每人一行：原稿落点 vs 重写落点，一句话一条，方便向评审人解释改了什么。
- 「待补数据」单独成表（谁／要什么／不补会被追问什么），不要藏在正文段落里。
- 文件按用户在 `98 hermes/02 绩效/高绩效上报/` 下对应季度目录，文件名带版本号，修订不改名只换号。
- 正文中凡不确定的数字，写 `〔待补：…〕` 并给候选值，不要自行编造；评审人已亲自讲过的点（如某人的具体天数）数字错了最显眼。

## 八、AI 味替换表

| 原稿式写法 | 改成 |
|---|---|
| 学习能力迅速、主动担当意识强 | 具体天数 + 越过了谁的预期（同期新人在做什么） |
| 跨项目快速支援 | 上线期人力按计划撤出后，他一人保住了哪个节点，部门因此腾出多少人力 |
| 攻坚复杂功能重构，推动核心模块成功上线 | 重构解决了什么问题（效率／对人的要求下降／后续可迭代） |
| 具备较强的系统理解能力 | 他能独立判断什么，而别人必须等谁拍板 |
| 主动拓展职责边界 | 他具体做了哪件岗位不要求他做的事，结果是什么 |
| 综合评价：表现突出，建议给予激励 | 删掉，换成部门激励导向 |
| 在仅留其一名 DE 的情况下…… | 人力按计划撤出后一人承接全项目现网闭环（含非本人开发模块） |

## 九、汇报顺序

一批人一起报时，按能力层级排列，让评审人看到激励梯度而不只是名单：**新人越级 → 专业深度 → 带队能力**。并在开头点明「这三个人的共同点不是比别人多干了活，而是做到了同岗位本来不要求的事」。
