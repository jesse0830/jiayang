# 内部流程创新报告 — 参考模板

## 适用场景

撰写**交付中心 / 软件工厂 / 技术团队内部AI赋能和创新实践**的综合性报告。这类报告的特点是：

- 不是单一客户项目，而是**内部团队在多个环节引入AI/工具提效的实践总结**
- 覆盖交付全流程的多个独立场景（如调研→设计→开发→测试→上线）
- 每个场景有独立的验证数据、问题分析和效率对比
- 最终需要跨场景的总结提炼（通用经验、可复制性评估、推广建议）
- 报告受众：**公司管理层**（如CEO/CTO、部门负责人），用于展示成果和争取资源

## 与最佳实践案例报告的区别

| 维度 | 最佳实践案例报告 | 内部流程创新报告 |
|------|----------------|-----------------|
| 核心对象 | 一个客户项目 | 内部团队多个创新实践 |
| 叙事主线 | 解决客户问题的过程 | 团队在各环节提效的方法 |
| 场景数量 | 1个 | 3-5个独立场景 |
| 验证数据 | 项目级交付数据 | 每个场景的实验/验证数据 |
| 受众 | 外部客户/售前场景 | 内部管理层/团队分享 |
| 侧重点 | 客户价值+可复制方法论 | 效率提升+资产沉淀+推广路径 |

## 标准结构（4-5场景版本）

### 第1章：项目概述

- **团队定位**：简短说明这个团队做什么的，为什么需要AI赋能
- **场景概览表**：用表格列出所有场景、覆盖的交付环节、解决的问题、当前成熟度

```markdown
### 1.X 场景概览

| 场景 | 交付环节 | 解决的问题 | 当前状态 |
|------|---------|-----------|---------|
| 场景A | 设计 | 用AI替代手动XX | 已验证，可用率XX% |
| 场景B | 开发 | 用工具替代人工XX | 工期压缩XX% |
| ... | ... | ... | ... |
```

### 第2~N章：每个场景独立成章（结构如下）

每个场景保持完全一致的结构，方便阅读对比：

#### X.1 场景说明
用1-2段描述业务场景。说明**传统方式是什么、有什么问题、尝试了什么新方法**。建议用实际项目名称增加可信度。

#### X.2 输入件与产出
用表格列出输入件、核心工具、交付产出。

| 栏目 | 内容 |
|------|------|
| **输入件** | 什么材料进入这个流程 |
| **核心工具** | 用了什么工具/AI/系统 |
| **交付产出** | 最终交付什么 |

#### X.3 验证结果
用表格呈现验证数据。关键指标：
- 测试量（生成了多少、覆盖了多少资产）
- 成功率/可用率/准确率
- 对比基准（传统方式的时间和效果）

#### X.4 问题分析
每个场景写2-3个当前存在的问题。每个问题包含：
- 问题描述（具体现象）
- 根因分析/影响范围
- （可选）后续优化方向

**命名规范**：问题一、问题二，用**粗体**标问题名。

#### X.5 SOP流程（可选但推荐）
用代码块（\`\`\`）写出标准的操作流程，供新人参考。5步左右，每步有具体动作。

#### X.6 效率提升分析
用对比表展示传统方式 vs AI/工具介入后的差距。

| 对比 | 传统方式 | 新方式 |
|------|---------|-------|
| 周期 | N天 | N小时 |
| 人力投入 | 需要XX全程参与 | XX做审核把关 |
| 修改成本 | 高 | 低 |

### 第N+1章：各场景效率提升总结

用汇总表横向对比所有场景：

| 场景 | 传统方式 | AI/工具介入后 | 效率提升 | 当前成熟度 |
|------|---------|-------------|---------|-----------|
| 场景A | X | Y | **约XX%** | 可用率XX%，需优化 |
| 场景B | X | Y | **约XX%** | 已验证有效 |
| ... | ... | ... | ... | ... |

### 第N+2章：经验总结与可复制性

#### 核心经验（每条独立成一小节）

**经验一：XX**

每个场景用一句话说明这个经验如何体现：
- 场景A：具体表现
- 场景B：具体表现
- 场景C：具体表现

**结论**：一句话总结。

**经验二：XX**
...

推荐用3-4条经验。如果覆盖了交付全链路，可以加入一条"全链路AI赋能"的经验，用流程图展示：

```
调研 → 设计 → 开发 → 测试 → 上线
         ↓      ↓      ↓
        AI/工具  AI/工具  AI/工具
```

#### 可复制性评估

用星级评分（⭐）评估每个场景的可复制性，并列出前提条件。

| 场景 | 可复制性 | 前提条件 |
|------|---------|---------|
| 场景A | ⭐⭐⭐⭐⭐ | 需要XX支持 |
| 场景B | ⭐⭐⭐⭐ | 需要优化XX |
| ... | ... | ... |

#### 推广建议

按时间维度分阶段：

**短期（1-2个月）：**
1. 立即可以做的事项
2. ...

**中期（3-6个月）：**
1. 需要一定投入的优化
2. ...

**长期（6个月+）：**
1. 体系化的建设目标
2. ...

### 报告元信息

结尾用引用块：

```markdown
> **报告版本**：vX.X
> **编制时间**：XXXX年X月
> **编制依据**：XXX团队在X、X、X场景的项目实践数据
```

## DOCX 同步工作流

当用户编辑了 .docx 源文件（如增加了一个新场景章节），要求我同步更新报告时：

1. **先读取 .docx 内容**：用 `python3 -c "from docx import Document; doc = Document(path); [print(f'[{i}] [{p.style.name}] {p.text}') for i, p in enumerate(doc.paragraphs)]"` 提取段落
2. **识别新增/修改的内容**：对比现有报告章节和 .docx 的新内容
3. **判断变更类型**：
   - 新增场景 → 新增一个完整章节（结构要和其他场景一致）
   - 修改数据 → 更新对应场景的验证结果/问题分析
   - 修改描述 → 定位到对应章节做局部更新
4. **更新全局内容**：
   - 第1章的场景概览表增加新行
   - 总结表增加新行
   - 经验总结中增加对新增场景的引用
   - 推广建议中增加新增场景的优化方向
   - 更新报告版本号 + 编制依据

## 常见陷阱

- ❌ 每个场景的结构不一致（有的有SOP有的没有、有的有表格有的没有）→ 必须统一
- ❌ 新增场景后，忘了更新概览表、汇总表和经验总结 → 三处必须同步更新
- ❌ 经验总结写得太泛（"AI很重要"）→ 必须从每个场景中提取具体的体现方式
- ❌ 缺少推广建议的时间维度 → 分短期/中期/长期，给出可执行的规划
- ❌ 只写成绩不写问题 → 每个场景必须包含问题分析，这是报告可信度的关键
