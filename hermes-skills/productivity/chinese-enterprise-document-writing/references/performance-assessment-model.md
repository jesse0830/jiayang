# 软件工厂月度绩效考核评估模型设计（方法论 + 实例 v1.0）

适用于：软件工厂厂长为 DE/IE/AE/数据开发设计月度绩效考核模型的咨询任务。
用户（杨嘉阳，数睿数据软件工厂厂长）2026-08 首次提出，已产出 DE 版 v1.0 草案。

## 用户业务背景（SmarDaten 数睿数据）

- 工具链：**鉴策行**（PM 每周五提订单的系统）→ **合契枢**（软件工厂任务管理/排产工具）。
- 排产维度：AE / DE / IE / 数据开发订单。注意 **AE 已从软件工厂划到项目产品部**，但排产维度仍含 AE。
- 合契枢模块：任务处理 / 缺陷处理 / 任务跟踪 / 产出统计 / 销售赋能 / 应用管理 / 任务分配 / 变更记录 / 周代码 / 字段配置 / 导出数据。
- 任务字段：周代码、编号、需求名称、任务名称、责任人、任务类型、任务复杂度（**极简/简单/中等/复杂 4级**）、任务备注、计划开始、计划完成、操作（变更/详情）。
- 当前 DE 考核现状：只看 IE 提的 bug 是否日清，未日清排名前五打 C（ABC 三级，C 扣绩效工资）。
- 用户关注点：项目产品部考核项目投入成本 → 工时审批建议交给 PM（PM 对项目成本负责，知情权最全）。
- 用户 2025 年人效模型分析：DE 是产能瓶颈（DE:AE=2.03:1），前10项目占50%产能。

## 绩效模型设计方法论（用户验证过的思路）

### 1. 四维权重框架（默认建议）
**月度得分 = ①任务达成40% + ②交付质量35% + ③协作贡献15% + ④过程合规10%**

| 维度 | 指标 | 数据来源 |
|---|---|---|
| ① 任务达成 40% | 按时完成率 + 产出量 | 任务处理/任务跟踪/产出统计 |
| ② 交付质量 35% | bug日清率15% + 缺陷密度12% + 返工率8% | 缺陷处理 |
| ③ 协作贡献 15% | 复杂/攻坚任务承担 + 跨项目支持 + 现场支撑 | 任务分配/申报 |
| ④ 过程合规 10% | 工时填报合规6% + 变更响应4% | 工时(PM审批)/变更记录 |

### 2. 度量单元问题（关键坑）
PM 以**大模块**为主要任务下发，难以拆分到任务级难度。方案三选一：
- A. 直接用合契枢「产出统计」模块现有数据（最省事，需先确认模块内容）
- B. 模块类型权重：Σ(完成模块 × 类型权重)。新功能开发1.0 / 迭代改造0.8 / 专项攻坚出差1.2 / 保障支撑0.5
- C. 排产人天：当月完成模块对应的人天（与排产/财经口径一致，**推荐**）
难度4级（极简0.5/简单1.0/中等2.0/复杂3.5）只作参考标注，不直接进公式。

### 3. 任务外工作补偿机制（用户强调的重点）
突发紧急任务（来不及建单）、现场bug支撑、出差攻坚项目都不在合契枢体系内：
- 突发任务：3天内**事后补录**进合契枢（标注"应急补录"），计入任务达成
- 现场支撑：月末**申报制**，组长/PM确认后折算等效产出（支撑1天≈系数2，攻坚1天≈系数3.5）
- 出差攻坚：**单独赛道**，不参与当月常规排名，按项目里程碑+PM评价定档
- 总产出 = 合契枢任务产出 + 补录产出 + 申报折算 + 攻坚等效

### 4. 分档与红线
- ABC 比例建议：A≤20% / B 60-70% / C 10-20%（避免"前五强制"引发内耗）
- C 判定 = 得分末位 + 红线触发（双条件）
- 红线（一票C）：生产事故/客户投诉、bug未日清超3天、工时虚报查实
- 豁免：需求变更/环境问题可豁免；出差期间 bug 日清按项目现场口径

### 5. 落地路径
1. 确认合契枢数据能力（产出统计内容、导出字段、是否支持补录）→ 2. 与PM对齐（人天估算/模块类型标注/审批接受度）→ 3. 做月度评分Excel模板 → 4. 试跑1-2个月不公示 → 5. 公示+申诉通道 → 6. 对接财经（PM审批工时按项目归集）

## 简历评语润色（招聘场景）

用户（软件工厂在招 DE/IE/运维/数据开发）会让负责人写评语，常太简单（如"技术栈满足、愿意加班、沟通不错"）。
润色方法：
1. **读候选人简历**（PDF 用 pymupdf 提取文本，`python3 scripts/extract_pymupdf.py file.pdf`），提取可验证事实（年限、技术栈、指标如 MTTR、证书）
2. 保留原评语三点意思，**不夸大**（说"高度匹配/可独立上岗"而非"技术顶尖"）
3. 给两个版本：完整段落版（适合直接填写）+ 分条精炼版（保留原结构）
4. 用简历事实支撑每条评语（年限/证书/具体指标），避免空话

## 厂长面试评论风格（用户亲授模板，2026-08）

用户展示过自己的评论风格，**终面评论必须按此格式**，不要自由发挥成段落/表格。结构固定：

```
<开头段：一句话基本情况> 学历年份+院校+专业（说"专业对口"与否）+经验年限+实际项目经验
技术能力：
1. <技术基础是否扎实 + 对该领域有无个人理解>
2. <技术面广度：列具体技术栈>
沟通能力：
1. <性格标签，如"标准的技术型性格，沟通较为直接不绕弯">
2. <逻辑思维能力，能否讲清楚做的业务功能/技术>
综合能力：
1. <加班态度/目标感>
2. <技术钻研意愿>
3. <工具/平台使用经历（如低代码配置）>
4. <职业规划描述：先沉淀→逐渐主导→最终独立交付>
5. <出差/加班接受度 + 南京长期发展意愿>
```

风格要点：
- 每条 1 句，简洁直接，无空话套话
- 分条编号用 `1.` `2.`（阿拉伯数字+点），不加粗小标题内文案以外的内容
- 开头段是"一句话"式概述，不含"评价"形容词
- 综合能力每条都以候选人的**实际行为/背景**支撑（如"实习期间加班较多"），不写评价性空话
- 给用户前先确认是否补充简历外信息（如"家里有亲戚在南京"这种面试中才了解的信息，简历里没有就不要编）

样例（用户原话风格，2026应届数据岗）：
> 2026应届毕业生，郑州财经学院大数据专业，专业对口，在郑州实习一年，有实际的数据治理相关项目经验。
> 技术能力：1.数据治理的基础技术能力比较扎实，对离线大数据有个人的理解；2.技术面比较广，对linux、python、shell脚本都有一些学习；
> 沟通能力：1.标准的技术型性格，沟通较为直接不绕弯；2.有一定的逻辑思维能力，能够讲清楚实习期所做的业务功能以及使用的技术；
> 综合能力：1.实习期间加班较多，并且对为达成目标而产生的加班能够接受，有较强的目标感；2.技术思维，喜欢在技术领域持续钻研深耕；3.有低代码配置的使用经历，并且愿意做一些配置操作；4.个人职业规划比较清晰，先沉淀技能，逐渐能够主导指标设计，最终能够独立交付项目；5.能够接受出差和加班，家里有亲戚在南京，想要在南京长期发展
