# PM Demand by Project Tier Model (基于项目分级的PM需求模型)

## 核心原理

PM（项目经理）的需求量不由**总收入**决定，而由**项目个数×项目复杂度**决定。一个小项目（20万）和一个大项目（400万）对PM的精力和管理带宽消耗相似——都需要沟通协调、里程碑跟踪、风险管控、客户对接。

## 苍南基准校准

### 已知参考值

| 项目 | 合同额 | 周期 | 全职PM数 | PM承载率 |
|:----|:-----:|:---:|:-------:|:--------:|
| 苍南 | 400万 | 1年 | 3-4人 | ~114万/PM/年 |

### 推导公式

```
PM承载率 = 合同额 ÷ (PM数 × 项目周期年)
苍南: 400万 ÷ (3.5人 × 1年) ≈ 114万/PM/年

应用于各 tier:
  大项目 (>=100万): PM承载率 100-200万/PM/年 → 1个项目≈1个PM
  中项目 (30-100万): PM承载率 ~50万/PM/年 → 1个PM带2-3个
  小项目 (<30万): PM承载率 ~10-15万/PM/年 → 1个PM带4-6个
```

## 三 Tier 匹配规则与适用场景

| Tier | 金额范围 | PM匹配规则 | 典型场景 | 所需PM数计算 |
|:-----|:-------|:---------|:--------|:----------|
| L (大) | >=100万 | 1-2个PM全职跟1个项目 | 苍南(400万)、智慧城市(500万) | count(L) × 1.5 |
| M (中) | 30-100万 | 1个PM带2-3个 | 某局信息化(80万)、数据平台(60万) | count(M) ÷ 2.5 |
| S (小) | <30万 | 1个PM带4-6个 | 定制报表(15万)、专项(20万) | count(S) ÷ 5 |

### 匹配规则弹性说明

实际PM需求取决于**项目复杂度**而非仅金额。同一tier内：
- 多客户/多干系人项目 → 更多PM精力
- 标准交付项目 → 较少PM精力（可复用经验）
- 首次合作/新行业 → 更多PM精力（磨合成本）
- 驻场项目 → 与在远程项目不同（驻场费用已含PM）

建议在计算时给出**低-中-高**三档取值，而非单点值：

```python
pm_demand = {
    'large':   count_large * 1.5,   # 范围 1.0-2.0
    'medium':  count_medium / 2.5,  # 范围 2.0-3.0
    'small':   count_small / 5.0,   # 范围 4.0-6.0
}
```

## 数据提取与分类（Python）

```python
import pandas as pd
import numpy as np

# 读取收入明细表（Format A）
df = pd.read_excel('25年收入-项目.xlsx', sheet_name=0)
df['收入金额'] = pd.to_numeric(df['收入金额'], errors='coerce')

# 如果单位是元，转为万
df['金额_万'] = df['收入金额'] / 10000

# 过滤年份——假设有收入日期列
df['收入日期'] = pd.to_datetime(df['收入日期'], errors='coerce')
df_2025 = df[df['收入日期'].dt.year == 2025]

# 按项目名称聚合（同一项目多笔收入合并）
# 这样可以识别"同一个项目签了400万，分批认收"的情况
project_totals = df_2025.groupby('项目名称')['金额_万'].sum()
print(f"总项目数: {len(project_totals)}")
print(f"总收入: {project_totals.sum():.2f}万")

# 三 tier 分类
large   = project_totals[project_totals >= 100]
medium  = project_totals[(project_totals >= 30) & (project_totals < 100)]
small   = project_totals[project_totals < 30]

print(f"\n>=100万: {len(large)} 个项目, {large.sum():.2f}万 ({large.sum()/project_totals.sum()*100:.1f}%)")
print(f"30-100万: {len(medium)} 个项目, {medium.sum():.2f}万 ({medium.sum()/project_totals.sum()*100:.1f}%)")
print(f"<30万: {len(small)} 个项目, {small.sum():.2f}万 ({small.sum()/project_totals.sum()*100:.1f}%)")

# 注意：如果有空项目名，需要单独处理
empty_projects = df_2025[df_2025['项目名称'].isna() | (df_2025['项目名称'].str.strip() == '')]
if len(empty_projects) > 0:
    print(f"\n⚠️ 警告: {len(empty_projects)} 行无项目名称，共 {empty_projects['金额_万'].sum():.2f}万")
```

### 关键：按项目名聚合 vs 按行统计

| 方法 | 含义 | 适合场景 |
|:----|:-----|:--------|
| 按行统计 | 逐笔入账计数 | 跟单、回款管理 |
| **按项目名聚合** | 同一项目多笔合并 | **PM需求推算**（这才是正确的） |

**如果不聚合的风险：** 一个400万的项目分6笔入账，会算成6个"项目"，导致小项目计数虚高，PM需求高估。

## 完整计算示例：2025年数据

### 原始数据
- 总收入: 3185万
- 总行数: 125行（同项目合并后）
- 数据来源: 25年收入-项目.xlsx，过滤仅2025年

### 分组结果

| Tier | 项目数 | 占比(个数) | 金额(万) | 占比(金额) | PM需求(中值) |
|:-----|:-----:|:---------:|:--------:|:---------:|:-----------:|
| >=100万 | 16 | 12.8% | 1551 | 48.7% | 16×1.5=24人 |
| 30-100万 | 14 | 11.2% | 671 | 21.1% | 14÷2.5≈6人 |
| <30万 | 76 | 60.8% | 964 | 30.3% | 76÷5≈15人 |
| 其他(空项目名) | 19 | 15.2% | — | — | 需确认 |

**注意：空项目名的处理** —— 如果有`在途收入`、`历史遗留收入`等非项目名称，需向用户确认这些是否占用PM资源。如果不占用，排除；如果占用，让用户补充项目名后再分类。

### PM总需求推算

```
PM总需求 = L + M + S = 24 + 6 + 15 = 约45人
```

对比：当前PM团队26人（含部长）+ 新增4人 = 30人。

**差额：45 - 30 = 缺约15个PM**（如果按1:1比例配，不含提效）

### 提效场景下的PM需求压缩

如果引入PM+AE结对模式（提升PM管理宽度30%）：

```
提效后PM管理能力 = 当前PM能力 × 1.3
等价于: PM需求压缩为 45 ÷ 1.3 ≈ 35人
现有30人 → 仍缺5人
```

## 与收入基线的交叉验证

### 校验方法1：PM占比校验

收入模型给出 PM:AE:DE:IE:数据 = 1:1:3:1:1，PM占比=1/7≈14.3%。

```
按全量HC模型：总需求209人（不提效）× 14.3% ≈ 30个PM
按项目分级模型：45个PM
```

**如果分级模型 > 总量模型** → 说明PM确实紧缺，需要调整配比（如PM占比从1/7提升）

### 校验方法2：份额法

```
PM需求占总HC的比例 = 45 ÷ 209 = 21.5%
标准配比中 PM占比 = 14.3%
PM溢出 = 21.5% - 14.3% = 7.2%
```

这意味着要么：
- 提升AE/DE/IE的配比来解决（PM减少？不合理）
- 或提效工具必须覆盖PM环节（PM+AE结对模式可以释放PM产能）
- 或管理层接受PM超配

### 校验方法3：大项目实测

一个有100万+项目的组合：

```
苍南(400万): 3.5个PM
宿迁(200万): 1.5个PM (对标苍南的一半)
812平台(100万): 1个PM
3个项目合计: 6个PM (实际在岗)
```

对照分级模型：
- >=100万: 3个 → 3×1.5=4.5个PM（低配了，实际6个）
- 原因：苍南驻场需要更多PM（每天沟通多），且跨地域

## 常见陷阱

### 陷阱1：小项目个数远多于大项目，但金额只有一小部分

这是最常见的模式（80/20法则的变形）。直接后果是：

```
按金额算：小项目只占30%收入 → "不需要太多人"
按个数算：小项目占78% → "需要的是PM精力，不是开发人力"
```

**解决：** 小项目组里的PM需求不是减少，而是每个小项目消耗的PM精力与金额不成比例。如果1个PM带6个小项目，那78个→13个PM。但用户可能会觉得"带6个太多了"，所以建议给弹性区间。

### 陷阱2：空项目名/合并行被忽略

Excel中常有：
- `在途收入`（非具体项目）
- `其它零星`（模糊类别）
- `维保服务`（非项目型收入）

这些要么排除，要么确认为具体项目后再归类。

### 陷阱3：同一项目名但有多个合同阶段

如"苍南"在2025年认收274.5万（合同总额400万）。按**当前认收额**分会在>=100万组，但如果只看2025年认收额，会低估项目规模。

**最佳实践：** 问用户合同总额（而非认收额）来分类。或者用已知的大型合同补充标注。

```python
# 可用用户提供的 override 表修正
overrides = {
    '苍南项目': 400,  # 合同400万，非2025年认收274.5万
    '某大型项目': 500,  # 总合同额
}
```

### 陷阱4：PM本身也分级别

大项目可能需要高级PM（总监级），小项目可能PM（专员级）就够了。如果按人头统一算，高级PM短缺而低级PM富余的情况会被掩盖。

**建议：** 如果有人员级别数据，进一步分解为 PM Senior / PM Junior。
