# HC缺口分析方法论

用于HC规划文档中，基于项目金额、人效数据和角色配比模型，计算各区域人力需求与缺口。

## 收入分解模式：百分比拆分（30%/70%模式）

用户（杨嘉阳）在多次HC迭代中，以**百分比拆分**方式提供收入构成，而非逐笔排除首付款/质保款。这是一个标准化的输入模式：

### 标准输入模式

用户说类似：「下半年月均1,200万收入，其中**30%是历史项目**（约360万/月），不需要工厂参与；**70%是新收入**（约840万/月），需要工厂支撑。」

### 计算转化

```
月均总收入 = 1,200万
历史项目比例 = 30% → 360万/月（不需工厂深度参与）
新收入比例 = 70% → 840万/月（需工厂支撑）

对于HC计算：
  有效需求收入 = 840万/月 × 5.5个月（H2剩余）= 4,620万
  有效年化收入 = 4,620万 / 5.5 × 12 = 10,080万/年
  对比去年有效产能3,185万（经排除后），增长约3.16x
```

### 关键要点

- **历史项目不需要工厂**意味着该部分收入对应的HC需求为0，不纳入缺口计算
- **新收入需要工厂支撑**意味着该部分收入全部需要增加人员产能
- 用户提供的百分比可能是近似值（30%/70%），不需要精确到个位数
- 这个模式与方总说的「2,000万已生产完待拿」是同一个逻辑的不同表达方式：30%×7,200万=2,160万，接近方总说的2,000万
- 如果用户说「不需要工厂参与」，要明确这意味着：不需要新增人员、不需要新组建项目团队、这部分收入由现有人员或已交付项目消化

## 三分类收入分解模式（PO类驻场 + 已生产完 + 项目交付）

在 HC 规划中，总收入不是按同一公式计算人力的。该用户的 SmarDaten 场景下，收入必须分解为三个互斥的类别，每类有独立的 HC 计算方法：

| 收入类别 | 含义 | HC计算方式 | 示例 |
|:---------|:-----|:-----------|:----|
| **已生产完待拿** | 历史项目已完成交付，只等客户付款（首付/质保/验收尾款） | **HC需求=0** — 不占人力 | 2000万（约28%） |
| **PO类驻场** | 按人头/人天计价的项目，客户按固定单价×人数付费 | **HC=收入÷人均固定费率÷月数** — 费率固定，不参与提效模型 | 800万（约11%），3万/人/月 |
| **项目交付** | 常规合同项目，需要工厂投入交付能力 | **HC=收入÷提效后人效** — 参与提效模型 | 4400万（约61%） |

### 计算示例（用户2026H2实际场景）

```
总收入目标: 7200万（月均1200万）

三分类分解:
  A) 已生产完待拿: 2000万 → HC 0人（无需工厂参与）
  B) PO类驻场: 800万 → HC = 800÷3万/人/月÷6月 = 44人
  C) 项目交付: 4400万 → HC = 需按人效公式计算

总需求人力 = 0（A） + 44（B） + X（C） = 44 + X
```

### PO类驻场的关键特征

- 费率固定（如3万/人/月），不随提效工具改变
- 人头可预测（收入÷固定费率=所需人数），不受项目复杂度影响
- **人效提升不影响PO类驻场** — 即使提效50%，PO类驻场仍需要44人（因为客户按人头付费）
- PO类驻场团队可能需要与软件工厂编制分开统计（如南通22人是PO类驻场，独立于工厂125人之外）
- PO类驻场人员的招聘标准、技能要求可能与项目交付团队不同

### 全盘人力落地公式

```
整编人数 = 软件工厂项目交付人数 + PO类驻场总人数

需扩招人数 = 整编人数 − 当前已到位人数

其中：
  当前已到位人数 = 软件工厂现有HC + PO驻场已到位人数（如南通22人）
  PO驻场还需招聘 = PO类驻场总人数 − PO驻场已到位人数（如44-22=22人）
```

### 与首付款/质保款排除的关系

三分类模式与首付款/质保款排除是**可根据用户当前口径选择使用**的关系：

- **旧口径（历史）**：先剔除首付款/质保款，算出真实人效基准，再用三分类模式部署未来人力
- **新口径（2026年7月会话后）**：首付款/质保款**不剔除**，直接拿总收入÷总人天算人效，再用该人效算未来HC

**⚠️ 永远不要默认使用上次的结论。** 每次会话开始时先跟用户确认：「这次算人效，首付质保要剔除还是包含？」

### ⚠️ 关键概念纠正：人天折合人数 ≠ 在岗人数

**这是最容易翻车的概念混淆，必须牢记：**

```
人天折合人数 = 总投入人天 ÷ 22天/月
在岗人数 = 实际在编在岗的人员数（从通讯录/花名册统计）
```

**区别：**
- 人天折合人数是"如果每个人满负荷工作，需要多少人"的理论值
- 在岗人数是公司花名册上的真实人数
- 两者差异来源于 **产能利用率**（不是每个人每天都在满负荷做项目交付）
- 用户公司产能利用率约64-69%，所以人天折合人数 ≈ 在岗人数 × 65%

**典型翻车场景：**
```
H1总投入8,687人天 → 折合 = 8,687 ÷ 6月 ÷ 22天 = 66人
用户纠正："不是66人，是102人"
原因：剩下的36人在做非项目工作（培训/管理/运维/售前支持/请假等）
```

**正确工作流：**
1. 先问用户：「现在实际在岗多少人？」
2. 用实际在岗人数作为 HC 计算的基准
3. 人天折合数只用于**人效基准计算**（收入÷人天），**不用于编制规划**
4. 在文档中分别标注：
   ```
   总在岗人数：102人（含管理/非交付角色）
   项目有效投入：8,687人天（折合约66人满负荷）
   产能利用率：66/102 ≈ 64.5%
   ```

## 乘法叠加提效模型（多个独立工具作用于不同环节）

当提效工具（每个 1.3x）作用于项目交付流程的**不同环节**时，它们**乘法叠加**而非加法累加：

```
综合提效系数 = 工具1系数 × 工具2系数 × 工具3系数 × ...
例如：1.3 × 1.3 × 1.3 = 2.2倍（提效120%）
```

### 适用条件

仅当多个工具满足以下条件时才可用乘法叠加：
- 每个工具作用于**不同流程环节**（如 PM+AE结对→立项设计 → 原型工具→需求转原型 → AE+DE协作→开发实现）
- 环节之间**无重叠**（一个任务不会被两个工具同时提升）
- 每个工具独立生效，互不依赖

### 典型场景（2026年H2实际案例）

| 工具 | 作用于 | 系数 |
|:-----|:-------|:----:|
| PM+AE结对 | PM效率释放，管理更多项目 | 1.3x |
| 交付中心需规与原型生成工具 | AE原型输出效率 | 1.3x |
| AE+DE原型驱动协作模式 | DE开发效率（从理解需求→服务编排） | 1.3x |
| **综合** | — | **1.3×1.3×1.3=2.2x** |

### 计算对比

```
不提效：人效 0.185万/人天 → 5,200万需 28,108人天 → 209人
提效后：人效 0.406万/人天 → 5,200万需 12,808人天 → 191人
节省：18个HC
```

### 对比单场景提效法（旧模式）

| 模式 | 含义 | 适用场景 |
|:----|:-----|:--------|
| **单场景提效**（旧） | 假设整体提效30%/40%/50% | 只有一个提效工具/策略时 |
| **乘法叠加提效**（新） | 多个工具独立生效后连乘 | 多个不同环节的工具同时实施时 |

**判断用哪种**：当用户列出3个独立工具，并说"每个都能提升30%"时，用乘法叠加。当用户说"整体提效大概多少"时，用单场景法。

## 简单线性外推法（用户未提供输入系数时的基准起点）

在用户说了收入目标（5,200万需投入）、基准数据（去年128人3,185万），但尚未提供提效系数/首付折扣/投入系数时：

**不要自己编系数。** 用最中性的计算作为起点：

```text
需求人力 = 需投入收入 ÷ 基准收入 × 基准人数
         = 5,200 ÷ 3,185 × 128
         = 约209人
新增HC = 209 - 当前120 = 89人
```

待用户补充提效系数后，再引入乘法叠加或场景分析。

**为什么必须用这个而不是自己编：**
- 如果自行假设首付款按50%折算，用户会说"谁让你打折了"
- 如果自行假设提效30%，用户可能只接受20%或50%
- 线性外推是"未经提效、未经折扣"的**中性地板上线**

## 核心计算逻辑

```
提效后月人均产值 = 年度人均产值 ÷ 12 × 提效后系数
需求总人力 = 项目总金额 ÷ 剩余月数 ÷ 提效后月人均产值
配比组数 = ceil(需求总人力 ÷ 每组总人数)  # 向上取整
各角色需求 = 配比组数 × 各角色系数
各角色缺口 = 各角色需求 − 各角色现有  (负值=富余)
```

### ⚠️ 关键概念纠正：收入 ≠ 产能（供背景理解）

**⚠️ 注意：以下内容是历史背景理解，不是当前操作方法。** 当前口径以用户最新指示为准（参见上文「与首付款/质保款排除的关系」）。

高层（如方总）在讨论人效时，常用"收入"作为产出指标，但不同收入类型的人天投入差异很大：

| 收入类型 | 示例 | 人力投入 | 旧口径算人效时？ |
|---------|------|---------|:--------------:|
| **终验/验收款** | 项目验收后到账 | 全周期投入 | ✅ 算 |
| **首付款** | 合同签订即付 | 几乎无需交付人力 | ❌ 旧口径剔除 |
| **质保款/维保款** | 项目交付后的尾款 | 极低维护人力 | ❌ 旧口径剔除 |

**为什么旧口径剔除（背景理解）：**
- 首付款和质保款是"已生产完待拿的收入"，不是当期交付创造的价值
- 如果直接拿总收入÷人数算人效，会**虚高人效指标**，导致管理层觉得"现有产能已经够高了"
- 方总明确提出：首付款、质保款等不需要或只需要极少人力投入的收入，算人效时必须剔除

**实践中的处理方式（历史参考）：**
1. 先问用户或高层：去年的收入中，哪些是首付款/质保款/已生产完待拿的收入？
2. 如果无法逐笔区分，确保报告中注明"含不可比收入项"的说明
3. 在缺口分析中做**双情景测算**：含全部收入 vs 剔除低投入收入后
4. 在文档中单独说明：**去年的"收入数字"不代表"产能数字"**

**当前（2026年7月后）：用户要求首付质保包含，做单情景即可。**

**特别场景：方总说的"去年月均600万"**
- 实际财务数据：月均265万（3185万÷12）
- 差异原因：方总的印象中包含了首付款/质保款/已生产完待拿的收入
- 这就是为什么必须**基于实际财务数据而非高管印象数字**做计算

### 实地验证：已知项目驱动

HC缺口的最佳验证方式是用**已知项目列表**反推需求，而非仅靠宏观金额。流程：

1. **从项目清单提取总金额**：从用户提供的规划图片/表格中OCR提取每个项目的金额，汇总得到总盘子
2. **验证剩余交付周期**：确认文档中写入的剩余月份与实际项目工期一致（如7月中~12月底 = 5.5个月，不是6个月）
3. **对账**：汇总金额与用户说的总目标做交叉验证。如有商机且落地概率低（如中远川崎智能体100W），可标记但暂不纳入硬性计算

**典型场景（南通2026H2实例）：**
- 通州高新集团11项目约830万（质量70W+支付15W+固资15W+公务员17W+集团KPI14W+基金30W+园区190W+财政20W+集团数字200W+费用10W+数据平台280W）
- 中远川崎2项目约190万（工务二期90W+智能体100W，后者商机落地概率低）
- 合计约1,020万 → 按1,000万计算

### 关键参数

| 参数 | 来源 | 示例值 |
|:----|:-----|:------|
| 人均产值 | 上一年度收入 ÷ 总人数（需剔除首付款/质保款等低人力投入收入） | 3,185万 ÷ 128人 = 24.88万/人 |
| 提效系数 | 人效工具综合评估 | 30%～50% |
| 配比模型 | 典型项目角色比例 | PM:AE:DE:IE:数据实施 = 1:1:3:1:1（每组7人） |

### 多场景分析

建议同时计算3个提效幅度（30%/40%/50%），给出范围而非单点值。

```
提效0%（基线）：56.25万/人
提效30%：73.1万/人
提效40%：78.8万/人
提效50%：84.4万/人
```

## 配比模型说明

配比模型来源于**典型项目的角色投入比例**，例如苍南项目的PM:AE:DE:IE:数据实施=1:1:3:1:1。

### ⚠️ 方总纠正：PM:AE 配比从 1:1 → 1:3

方总在 7/19 会议中明确要求：PM 和 AE 的配比从之前的 1:1 调整为 1:3。

**原因：**
- AE（应用工程师）主要做需求分析和设计，是人力投入最密集的阶段
- PM 负责项目管理和统筹，管理宽度可以覆盖更多 AE
- 1:3 配比让 AE 成为交付的"主力军"，PM 成为"管理核心"

**对缺口分析的影响：**
- 配比模型从 `PM:AE:DE:IE:数据实施 = 1:1:3:1:1` 变为 `1:3:3:1:1`（每组从 7 人→ 9 人）
- AE 的缺口会显著扩大
- DE 保持 3 不变

### 特殊情况：按人头驻场项目

苍南等**按人头驻场项目**不适合用配比公式计算：

**注意：**
- 运维、售前、行政、财务、商务等**非核心角色**不在配比模型内，但实际存在
- 实际人员中可能有**多角色兼任**的情况（如PM兼AE），按实际角色统计
- 配比模型是**按项目需求**计算的，而实际团队可能有**共享/支撑**职能
- **按人头驻场项目（如苍南）要单独列出**，不纳入配比公式计算。这类项目客户按人头付费，P 数固定，人员规模由客户需求决定而非收入比例决定。

### 特殊交付模式：按人头驻场项目

**定义：** 客户按交付人数付费（按人头×单价），而非按项目里程碑付款。

**典型场景：**
- 苍南项目 — 客户按 4-5 人长期驻场付费
- 其他县市政务网项目

**与常规 PO/合同项目的区别：**
| 维度 | 常规项目 | 按人头驻场项目 |
|:----|:--------|:-------------|
| 计价方式 | 按项目金额（合同价） | 按人头数×单价/月 |
| 人员规模 | 由收入/配比公式确定 | 由客户需求确定 |
| 可调整性 | 可调配增补 | P 数固定，不可随意增减 |
| 人效计算 | 按收入÷人数 | 按人头×单价直接计算 |

**HC 分析中的处理：**
1. 单独列出行：苍南项目 PM 1/AE 1/DE 3/IE 1 → 共 6 人（P数固定）
2. 不纳入配比模型计算
3. 如果驻场人员有缺口，按实际需要单独标注（如"需要增补1名DE"）
4. 在区域汇总表中单独统计，不与其他 PO/合同项目混算

## 人员数据核实流程

用户提供的名单与文档中已有记录往往存在差异，建议按以下流程核实：

1. **逐行审查**：用户提供的每一条"姓名+角色"都核对
2. **标记状态**：标注离职、调离、待确认
3. **去重统计**：按角色汇总，排除已离职和调离人员
4. **对比旧数据**：将实际统计与文档历史记录做差异对比
5. **更新文档**：差异较小时用patch更新，差异大时（如PM 5→3）建议直接替换整节

### 常见差异类型

- PM/DE等核心角色实际人数与文档记录不同（原记录过时）
- 新入职人员未在文档中体现
- 角色调整（如某人从AE转PM）
- 非核心角色（售前、行政、财务）之前未做统计

### 重要：确定性 vs 全部商机

华为（该用户所在公司）的订收回计划表通常有多个sheet：

- **全量Sheet**（如"订收回总表"或第1个sheet）：包含所有项目、PO、商机，汇总为一个大数字
- **确定性Sheet**（如"Sheet1"或"已确认"）：只保留已有PO/合同/确定落地的项目

**用户可能先给全量版，再给确定性版。** 两个版本的收入差异可能极大（如全量2,549万 vs 确定530万），因为大量商机型项目（算力尾款、智慧城市底座、智能体开发等）被剔除。

**处理流程：**
1. 拿到一份Excel时，先问「这个是含商机的全量数据，还是已确认的确定性数据？」
2. 如果用户后续给了一个新版本（如"用这个最新的Sheet1"），说明之前的版本不准确
3. 两个版本的数据都要留存，但**HC缺口分析以确定性计划为准**
4. 在文档中写：确定性计划下不缺人 → 多情景推演表（含大商机落地后的缺口）

#### 全局对比（区域汇总表更新）

当用户提供了各区域的实际数据后，汇总表需要整体更新。注意**联动更新效应**：

- 南通人员更正 → 影响南通缺口 + 全区域合计
- 某区域目标变化 → 影响总需增补数 + 缺口占比描述
- 描述文案也要同步更新（如从"成都为主"改为"南通+成都双战场"）

## 固定参数比例缩放法（Fixed Parameter Scaling）

与收入驱动的HC计算法和项目分级PM需求模型并列的第三种方法论。适用于：用户给定了某一角色的编制上限（如"PM=30人"），需要在**当前产出效率不变**的前提下，推算其余角色的需求和缺口。

### 与前两种方法的区别

| 方法 | 输入 | 输出 | 适用场景 |
|:-----|:-----|:-----|:---------|
| **收入驱动法**（Revenue-based） | 目标收入 + 人效基准 | 总编制（各角色相加） | "H2要干7200万，需要多少人？" |
| **项目分级PM模型**（Project-tier） | 项目清单（收入+数量） | PM需求人数 | "现在这么多项目，PM够不够？" |
| **固定参数缩放法**（Fixed-Parameter） | 某角色编制上限 + 实际配比 | 其余角色编制 | "PM定30人，下游怎么配？" |

### 核心计算逻辑

```
第1步：确定被固定角色（如PM）的编制数 N
第2步：从运营数据中获取当前实际产出效率：
  └ 每PM管理有效产出 = 当前下游总人天 ÷ 当前PM人数
第3步：推算新产出规模：
  └ 可管理总产出 = N × 每PM管理有效产出
第4步：按实际角色比例（AE:DE:IE:数据开发）分配各角色人天
第5步：折算为编制人数（÷ 260天/年）
第6步：对比当前实际人数，得出缺口
```

### 关键数据来源

- **下游总有效人天**：从收入-资源交叉匹配看板中获取，剔除内部/非收入项目
- **当前PM人数**：从组织花名册获取
- **角色有效产出比例**：从看板的AE:DE:IE:数据开发有效人天占比计算
- **内部/非收入消耗**：同样从看板获取，作为额外编制需求加回

### 实际案例（SmarDaten 2025数据）

**输入：**
- PM固定30人（当前26人）
- 当前每PM管理有效产出 = 15054人天 ÷ 26人 = 579人天
- 角色有效比例：AE=24.5%, DE=49.6%, IE=20.2%, 数据开发=5.8%
- 内部消耗：3083人天（17.0%）

**计算过程：**
```
30PM可管理有效产出 = 30 × 579 = 17370人天
含内部的总产出 = 17370 + 3083 = 20454人天

AE需求 = 20454 × 24.5% = 5010人天 → 5010÷260 = 19人
DE需求 = 20454 × 49.6% = 10148人天 → 10148÷260 = 39人
IE需求 = 20454 × 20.2% = 4264人天 → 4264÷260 = 16人
数据开发需求 = 20454 × 5.8% = 1032人天 → 1032÷260 = 4人
下游合计 = 79人

总团队 = 30(PM) + 19(AE) + 39(DE) + 16(IE) + 4(数据) + 维优维持 = 约136人
```

### 使用场景与限制

**适用：**
- 管理层给出某角色编制上限（"PM不超过30人"）
- 做增量优化（"不大幅扩编，先优化结构"）
- 用户想看到"在当前效率水平下，固定X角色人数后其他角色能力如何"

**限制：**
- 假设各角色效率比例在当前和未来保持不变 — 如果计划引入提效工具，需叠加提效系数
- 无法反映项目管理中的瓶颈效应（如PM是人力瓶颈但DE可能快速扩招）
- 仅适用于**同比例缩放**场景，不适用于收入大幅增长（如翻倍）的情况 — 后者需用收入驱动法

**与提效工具的关系：**
- 固定参数法给出的是"不提效基线"
- 叠加提效系数后：`各角色需求 = 当前计算值 ÷ 提效系数`
- 提效系数影响所有角色（或作用于特定角色，看提效工具覆盖范围）

## 常见陷阱

- **配比模型不适用所有项目类型**：驻场项目（如苍南）和PO项目（如中远川崎）的人员结构可能不同
- **人均产值是全局平均**，大型项目可能人效更高，小型项目可能更低
- **提效系数是预估**，实际落地效果取决于人效工具的推进情况
- **现有人员包含非交付角色**（售前/行政等）— 缺口分析时需区分核心角色和非核心角色
- **确定性 vs 全量混淆**：用户最初给的收入数据可能含大量商机（如2,549万），后续给的"Sheet1"版本可能只有确定性收入（530万）。分析结论可能完全反转。**永远在有明确标签（"Sheet1"、"确定"、"已确认"）的版本上做硬性计算。**
- **高层印象数字 vs 实际财务数据**：方总说"去年月均600万"，实际财务数据是月均265万。**永远以实际财务数据为基准**，高管印象数字（"月均600万"、"7200万目标"）可能严重偏高。在文档中同时展示两种口径并说明差异原因。
- **汇总表联动更新** — 一个区域的数据更正（如南通24→21人）会联动影响：
  - 该区域的缺口数字
  - 全局合计（95→?）
  - 全局描述文案（如"成都为主"→"南通+成都双战场"）
  - 需要在同一个patch pass中同时更新数据表+描述文案，否则用户会看到不一致
- **数据实施（数据开发角色）是常态化瓶颈** — 这是SmarDaten交付团队中最难招聘的角色，缺口分析时要特别标注。在多家区域（南通、成都）中都出现数据实施短缺，建议在风险章节中单独说明。
