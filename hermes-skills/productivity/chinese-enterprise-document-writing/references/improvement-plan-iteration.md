# 提质增效／提效方案：分轮补写与迭代约定

适用：用户拿着自己或他人写的内部方案（如《业务交付提质增效方案》），要求补写某一章（常见「效能提升方案」），并在后续若干轮对话里逐条追加／修正措施。

## 每轮交付形态（固定五步）

1. 稿子落文件（.md 放用户指定的归档目录），**用 patch 做定点修改，不要用 write_file 整篇重写**：长文档重写后工具回报的行数／节选可能与实际不符（内容回声被压缩），无法自证落盘正确；只改要改的那一块，其余保持原文。**同理不要用 execute_code 的 stdout 打印长段落或长文件做复核**（输出会被压缩截断、只回报 1 行，结论丢失）：要复核就 `read_file` 直接读，或写独立脚本 `> /tmp/xxx.txt 2>&1; echo exit=$?; wc -l` 再 read_file 那个文件。**`read_file` 一次要长区间也会回成 1 行（只报字数）——这不是文件坏了，换 20~40 行的小窗口分段重读即可**；要 patch 的锚点必须这样逐字取回。
2. 每次改动后 **grep 一次章节标题（`### 3.x` / `**（n）…**`）核对结构**，确认新增项在位、层级与顺序正确，再交付；**插入独立小节／重编号时再 read_file 复核一次总行数与子节标题序列**（patch 的 diff 不显示总行数变化，且 insert 后容易漏改引用句里的编号）。
3. 回复里给出**改动后那一条的全文**（不是 diff、不是摘要），用户要能直接复制进飞书／word。
4. 附 2~4 点「为什么这么写」，把用户的原始输入逐条映射到文稿里的句子——用户就是在核对这个映射。
5. 结尾列**待确认口径**，一次 1~2 个；不要堆成问题清单，也不要替用户拍板。

## 措施条目的标准结构

- 每条措施 = 措施 + 责任角色／决策人 + 验证口径（可观测指标，便于月度复盘）。
- **涉及阈值的条目，把口径本身写成一条独立要点**（例：金额分档按合同额判定、不看税率）。口径不写进正文，落地时必然出现两套说法。
- 子标题沿用原文章节的问题提法，不另造框架；新增子项必须能一一映射到原文某一类问题。
- **不新编数字**：只引用方案内已有基线（人天、字数、模块耗时等）；新增指标一律标注「试点期校准」。
- 与「对外汇报版本不放内部运营数据」的规则并存：补充稿只引用方案内既有基线，不引入产能利用率／目标／HC 缺口等内部口径。

## 分轮追加输入的处理

用户常一条消息只加一个措施（例：把设计文档改成配置文档、小项目自闭环、增加审核卡点）。收到后按序处理：

1. 判定它挂在第 2 章哪一类问题上（文档类／协作类／工具类／管理类），挂到对应的 3.x 之下。
2. 判断是**新子项**还是**已有子项里的一条**：同源（同一问题、不同维度，如「角色边界机械」→「按项目规模分通道」）并入已有子项；问题不同才新起子项。**加一条判据：这条内容的收益是否已被量化节点按条计列**——若它落在某条已有措施的作用范围内（例：运维侧前置 checklist 之于「环境与外部依赖前置确认」），一律**并入那一条、不新起条数**，只把量化表对应行的验证口径文字补上、**百分点与合计数字不动**；新起子项会让同一份工时在两处各计一遍。
3. 只改那一个块，其余不动。
4. 若输入隐含责任转移，主动补一个把关卡点（见下）。

## 「简化即新增风险」原则（本类方案最易漏）

任何「简化／放权／交给下游直接做」的措施，都会把风险从「上游写得不够细」转移到「没人审得够」。写措施时必须同时给出**审核卡点**：

- 谁审、审哪几项（逻辑是否闭环／能否被下一级独立执行／边界与权限是否写清）、审核时限、不达标怎么办（打回并分类记录原因，原因分布作为上游文档质量的度量）。
- 审核人由现有 TL／骨干兼任，**不新增编制**；承接人按阶段放行（带教 → 独立＋复核 → 抽查），每类任务都要走完三步，避免一刀切放行。
- 兜底两条：上游对复杂点保留可行性确认；需求有歧义时由单一角色在 1 个工作日内裁决，不让下游「对着空白猜」。

## 分级协作／阈值类措施

- 写清**判定口径与判定点**（按合同额还是毛利、在哪个评审节点判定），并明确「不允许后置到执行中才暴露」——那时加人加时间都来不及，还说不清是谁的决定。
- 分**默认通道**与**例外通道**：默认通道写清谁与谁自闭环、哪些重型流程不铺开；例外通道写清一次定清的三件事（以什么目标做／需要哪些角色参与／投入上限与收口条件）。
- 例外通道必须**约束提出方**（例：差额成因分类留痕＋按月统计复盘），否则例外理由（「战略性」「标杆」）会变成通用理由，压力全落到交付侧。
- 决策人写具体：谁提报、谁补充背景、谁裁决并留痕。

## 量化节里的「实测锚点」（用户给真实项目数据时）

- 单起一条「实测锚点」放实测数据，**不要拿它去覆盖或重算既有预估表**：预估表是方案基线（对外口径要稳），实测是证据；两套并存、互相印证。
- 实测与预估方向不一致时照实写实测，后面跟一句「该结论仍需在后续项目上继续验证」，并在样本说明里点出局限（例：驻场人天占比畸高、受驻场要求影响，作方向性锚点、不当配比平均值）。**预估数字是唯一不能漂移的东西**，不要为了自洽回头改它。
- 实测样本与用户口头口径有缝隙时（例：用户说「比例基本到了 1:1:1:1」，而四个角色里 IE 只占 6%），正文写「核心三角基本 1:1:1，IE 与二开各占少量」，并把这个缝隙作为待确认口径提给用户二选一，不要替用户圆。
- 实测数字**用代码按明细求和／算占比**，不要靠看截图读表：图里表格数字经常读不出来，汇报读数不如汇报汇总值＋占比。
- 实测值与预估值的差异本身要写成结论（例：某角色「由三倍降到等量」），这是整章最有力的证据，比任何估算都有说服力。

## 交付前后的自检

- 每条能否对上原文某一类问题？
- 有没有新编数字？新增指标是否都标了「试点期校准」？
- 每条是否都有验证口径？
- 简化类措施是否都配了审核卡点与兜底？
- 新增内容是否做过「并入已有条 vs 新起条」判定？新起的那条有没有把同一份收益在量化节里计第二遍？
- 有实测数据时：是否只作证据并列呈现，没有回头改预估表？样本局限是否写进正文？
- 内容是否已并入既有稿件的对应条目（而不是留成独立文件）？独立稿是否已从本地与 git 同步目录一并删除？
- 版本行是否**追加**（未覆盖旧行）？推送副本是否 grep 验证过新锚点在位？

## 融合：把新写的内容并回既有材料（多份稿子收成一份）

用户追加内容后常跟一句「这个文档和之前的文档融合到一起」——默认形态就是**内容并入既有稿件的对应条目，独立补充稿不保留**；确要留独立文件时先问一句。

**先判定位，再动笔。**同一段输入可以是「可落地的做法」，也可以是「某时段的工作安排」，方向写错整段会被否。判据：用户谈链路／角色／工具／可复用性 → 写成该措施的**落地执行方式**；用户谈时段／排期（节前节中节后、加班、补休）→ 才写排期。项目案例（某个在建项目）按前一种写：链路步骤、为什么可复制、复制时必须守的卡点、适用判定、落地后的度量项。假期窗口最多作次要理由（如工具链切换需要连续窗口），**不能当章节主轴**。

**先取锚点原文再动手。**patch 的 old_string 必须与磁盘逐字一致：用 read_file 小窗口（offset/limit 20~40 行）分段读回目标区间；若返回只报字数／1 行，说明输出被压缩，换更小窗口重读，**不要凭对话摘要里的转述改稿**（转述会把「实测配比约 1 : 1」这类口径写歪，也会让插入位置偏一格）。

**四处落点（缺一处就算没融合）：**
1. 对应措施条目末尾 → 加「落地执行形态」＋可复制性论证＋复制卡点＋适用判定＋落地后度量项，作为该措施的执行方式；**不新起小节、不改原有编号体系**。
2. 量化／指标节的实测锚点 → 新增锚点与原锚点**并列**，写明该项目的差异点（如某环节工作量占比更高）与「数据回填前本稿不引用该项目任何工时数字」。
3. 口径纪律条目 → 把「实测案例（A）为单项目样本」扩写为「（A、B）均为单项目样本」，未出数的案例写明「回填前不对外引用」。
4. 文件头**追加**一行版本记录（日期＋这次并入了什么、独立稿已撤销），旧版本行保留不覆盖。

**撤销独立稿与自证（三步收尾）：**本地 rm 独立稿；在 git 同步目录也 rm 同名副本、把更新后的主稿 cp 过去；commit+push 后 **grep 一次推送副本**（`grep -n '<案例名>\|<小节编号>' <同步目录文件>`）确认新锚点确实在推送件里——只报 commit hash 不算自证。

**数字纪律不变：**用户口述的项目口径（如原型可用率超过 90%、配置只用 30% 时间）可以直接引用，但统一标「试点期校准」；案例实测数字未回填时正文只写「待回填」，不新编、也不换算成工时。
