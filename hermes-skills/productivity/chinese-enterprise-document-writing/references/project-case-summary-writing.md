# 项目成功案例总结文档编写指南

用于协助用户编写结构化的项目成功/客户成功案例总结文档。

## 编写流程

### Step 1: 建立框架（用户提供的首批信息）

从用户获取最基本的信息后，立即搭建 Markdown 框架：

```markdown
# 项目成功与客户成功案例总结

---

## 案例一：[项目名称]

### 一、项目概况

| 字段 | 内容 |
|------|------|
| 项目名称 | ... |
| 客户名称 | ... |
| 我方公司 | ... |
| ... | ... |

### 二、项目背景
（待补充）

### 三、业务内容 / 解决方案
（待补充）

### 四、客户成功过程
（待补充）

### 五、客户成功亮点
（待补充）
```

### Step 2: 渐进式填充（用户逐段提供信息）

当用户分段提供信息时（如台州项目：先说干系人、再说业务内容、再说接手背景），**不要等全部信息再填**。每收到一段信息就立即：

1. 更新对应的章节
2. 保持"（待补充）"标记在其他章节
3. 如果信息涉及多人/多组织，用表格清晰展示

### Step 3: 干系人分析表

当用户提到项目参与方时，立即整理为结构化表格：

| 角色 | 姓名/单位 | 立场与诉求 | 应对策略 |
|:----|:----------|:-----------|:---------|
| 分管领导 | ... | ... | ... |
| 对接人 | ... | ... | ... |
| 承建方 | ... | ... | ... |

### Step 4: 分层的项目背景描述

包含：甲方 → 承建方 → 转包方 → 实际承建方，用表格清晰呈现层层转包/过单关系。

### Step 5: 客户成功过程的叙事结构

采用"接手烂摊子 → 5维调研 → 干系人分析 → 问题诊断 → 策略制定 → 关键转折 → 最终成果"的递进叙事：

1. **项目背景与接手情况**：坦诚描述项目困境（如已换3任PM、被认为烂尾）
2. **调研切入点**：招投标、业务内容、干系人、项目影响、项目性质判断（政绩型 vs 实战型）
3. **干系人分析**：识别推动者和阻力者，制定应对策略
4. **项目性质判断**：是政绩型（重汇报轻实效）、实战型（重落地轻包装），还是**双重属性**
5. **问题诊断与剖析**：将问题分两大类
   - **我方项目管理侧问题**（PM频繁更换交接断层、承诺无法兑现信任透支、远程缺乏温度忽视客户压力期）
   - **客户侧问题**（需求多变蔓延、客户要求高但PM无技术功底无法讨价还价）
   - 每个问题写清楚：痛点描述 → 具体表现 → 对项目的影响
6. **客户关系重建 / 关键转折点**：具体做了什么来扭转局面
7. **项目成果**：可量化的交付成果

### 信任重建策略模板

当用户描述如何扭转烂尾项目局面时，识别以下模式并结构化呈现：

#### 第一阶段：重建信任（小步快跑兑现承诺）

| 步骤 | 做法 | 目的 |
|:----|:-----|:-----|
| **深挖业务** | 围绕核心业务方针全面梳理，研究市场同类产品 | 建立专业话语权，能从业务合理性角度与客户博弈 |
| **现场驻场** | 直接奔赴客户现场，面对面沟通 | 用行动表态，打破"远程不重视"的印象；获取第一手需求 |
| **聚焦紧急问题** | 与客户梳理2~3周内必须解决的紧急问题清单 | 缩小范围，快速出成果 |
| **小步快跑交付** | 带技术一起评估，制定客户认可的时间计划并严格执行 | 用准时交付兑现承诺，重塑信任 |
| **灵活接受变更** | 此阶段无条件接受10%~20%的需求变更 | 展现配合诚意 |

**关键洞察：** 第一批承诺按时兑现是**重塑信任的最佳窗口期**。客户态度会从"完全不信任"转变为"愿意再试一次"。

#### 第二阶段：化被动为主动（从被需求牵着走到牵引客户）

当项目按计划平稳执行一段时间后，开始从被动响应转向主动引导：

1. **建立"我说了算"的专业地位** — 通过前几轮准时交付，让客户建立"交给他，结果是有保障的"的认知
2. **客户开始接受优先级判断** — 对于不重要的需求，客户愿意接受"后续处理"的安排
3. **系统性做减法** — 在确保客户可汇报成果不受影响的前提下，主动删减低优先级需求
4. **缓解后方压力** — 将第一阶段积压的团队压力逐步释放

#### 第三阶段：个人纽带建立

通过观察客户个人空间的线索（如办公室有羽毛球拍且位置经常变化），推断客户爱好，提前做功课，自然切入建立工作外的共同话题，形成固定互动节奏（如每周打球）。

**区域社交敏感性提示：** 不同区域客户社交习惯不同（如浙江客户忌讳与合作方吃饭应酬），需另辟蹊径（运动、兴趣等），不能默认使用酒桌文化。应在文档中注明客户的社交偏好。

### 变更沟通技巧

当需要向非技术客户解释变更成本时，使用**生活化类比**：

| 场景 | 类比 | 解释 |
|:----|:-----|:-----|
| 页面微调 | **"汽车补漆"** | 看似只修一个小点，但需要整个面来处理——前端组件化架构中单点改动涉及样式重构、兼容性测试、回归验证等 |
| 影响逻辑的变更 | 类比到客户熟悉的业务场景 | 拉回客户自己的KPI语境：变更影响质量 = 影响客户自身的业绩考核 |

### 验收策略模板

当项目经理的考核标准是"拿到验收"且客户关系到位后：

1. **识别客户考核核心** — 分析各模块对客户个人考核的重要性（如"引/用/育/留/管"中只有"育"是他的核心指标）
2. **差异化交付策略**：
   - ⭐ **核心模块**：高标准交付，全力保障
   - ⚪ **非核心模块**：功能存在、流程走通、监理能通过即可
3. **系统性瘦身** — 基于上述策略删减需求，量化节约成本（如节约110人天）
4. **成本节约的量化维度**：
   - 非核心模块需求删减（主项）
   - 变更管理成本降低（减少无效变更和返工）
   - 沟通效率提升（信任建立后减少反复确认的时间）

### 问题诊断的写作规范

当用户描述项目问题时，按以下结构组织：

```markdown
##### 问题一：[问题标题]

> [一句话概括，突出痛点和严重性]

**影响：**
- [对客户关系的影响]
- [对团队/交付的影响]
- [对项目整体的影响]
```

分两组：**我方项目管理侧问题**和**客户侧问题**，让读者清楚哪些是可控的、哪些是需要协作解决的。

### 关于多案例合并与分离

- 用户在编写过程中可能要求**只保留当前案例**（去掉其他项目）。应当立即执行，不要等用户多次提醒。
- 分离后保留文件路径不变，只改写内容。
- 如果用户后续要求合并，重新新建章节即可。
